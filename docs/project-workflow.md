# プロジェクト推進・レビュー対応ガイド

## 1. 目的

企画から公開までの判断、作業、レビュー結果を追跡可能にし、変更の意図と具体的な差分を確認しやすくする。本書は、Issue、マイルストーン、文書、ブランチ、Pull Requestを使う際の共通手順を定める。

## 2. 計画の管理

### Issue

作業Issueには、可能な範囲で次を記載する。

- **目的**：解決する課題と利用者への効果
- **対応内容**：実施する作業と範囲
- **完了条件**：レビュー時に確認できる状態
- **関連項目**：依存Issue、仕様書、設計書、参考資料

実装Issueは、対応する仕様・設計へのリンクと、変更後の確認方法も記載する。Issueの範囲が変わった場合は、本文と関連ドキュメントを同じタイミングで更新する。

### マイルストーン

マイルストーンは成果として確認できる段階で区切る。関連Issueを割り当て、範囲や順序に変更があれば、マイルストーンの説明とIssue割当を更新する。

### ドキュメント

仕様・設計を実装前に用意し、利用者向けガイドや運用手順を公開前に整える。サービス方針、要件、データ契約、構成の判断が変わったら、対応Issueと文書を更新する。技術・製品方針に関する記述は、現時点で採用する決定と将来の選択肢を区別する。

### 設計方針と再利用性

設計書を作成・更新する際は、再利用性を明示的な設計観点として扱う。共通機能、分野固有コンテンツ、拡張機能の責務と境界、公開契約、依存方向を記載し、特定分野の前提や条件分岐が共通機能に入り込まないよう確認する。可能な場合は別分野のサンプルで再利用性を検証し、再利用の条件や例外を設計書に記録する。

## 3. ブランチとPull Request

### 統合先

日常開発のPull Requestは `dev` を基準に作成する。`main` へ直接マージせず、公開やリリースのタイミングで、確認済みの `dev` の内容を反映する。例外的に統合先を変更する場合は、IssueとPull Request本文に理由を記録する。

- 1つのPRは、関連するIssueと一まとまりのレビュー目的に絞る。
- ブランチ名に変更の主題またはIssue番号を含める。
- 作業途中の結果はDraft PRとして提示できる。
- PR本文に目的、主な変更、関連Issue、確認状況を書く。
- PR本文に関連Issueを記載する。自動クローズ参照は、PRのマージ先がリポジトリの既定ブランチの場合に動作する。
- このリポジトリの日常開発PRは `dev` 宛てのため、`Closes #番号` を書いてもマージ時にIssueは自動で閉じない。`dev` へのマージ後、完了条件を確認してIssueを手動で閉じる。
- 公開環境での確認など未完了項目が残るIssueは閉じず、残作業と確認時期を記録する。既定ブランチ向けPRでは、自動クローズ参照を使用できる。
- 文書のみの変更でも、更新した文書と重要な判断をPR本文に示す。

### 作業ブランチの棚卸し

作業の完了時とPull Requestのマージ後は、GitHub上のブランチを確認し、不要な作業ブランチがあれば削除する。

- Pull Requestがマージ済みで、今後参照する必要がない作業ブランチは削除する。
- Pull Requestがなくても、空のブランチや、変更が統合済みで固有の作業が残っていないブランチは削除対象とする。
- 削除前にPull Requestの統合状態とブランチ固有のコミットを確認する。未マージの変更や独自の作業が残るブランチは保持する。
- `main`、`dev`、復旧用・退避用ブランチ、作業中のブランチは削除しない。
- 確認結果として、削除したブランチと保持したブランチを完了報告に記録する。

## 4. 指摘への対応とフォローアップPR

レビュー指摘を受けたら、影響範囲とレビュー単位を確認して対応方法を決める。

### フォローアップPRを作る場合

以下のいずれかに当てはまる場合は、指摘対応を独立したブランチ・PRに分ける。

- 変更が別ファイルや別機能に及び、単独でレビューできる
- 元のPRの主目的や範囲を変えず、修正を分けた方が意図を追いやすい
- 元のPRがすでにレビュー済み、マージ済み、またはそのままの差分を残したい
- 指摘に対する修正を個別に承認・取り消しできるようにしたい

元のPRに積み増す場合も、変更が小さく元のレビュー範囲に収まる理由を明らかにする。判断が分かれるときは、レビュー差分を独立して確認できるPRを優先する。

フォローアップPRでは、元のPRまたはレビュー指摘への参照を付け、何に対応する修正かを明記する。元PRが未マージの場合は、必要に応じて元ブランチをベースにしたPRとして積み重ね、差分が重複表示されないようにする。

## 5. 修正箇所の差分表示

変更の説明では、要約だけでなく、レビュー対象となる実際の修正箇所を示す。

- **文書**：ファイル名・見出しと、修正前／修正後の該当文を記載する。
- **コード**：該当ファイルと行を示し、短いunified diffまたはPR diffへの直接リンクを付ける。
- **IssueやPR本文**：指摘、修正箇所、具体的な変更内容を対応付ける。
- **複数箇所**：ファイルごとに分け、変更していない内容まで全文再掲しない。
- **削除を伴う場合**：削除対象の文言・挙動も差分に含める。

差分例：

```diff
- 修正前の仕様
+ 修正後の仕様
```

差分は変更後の内容と一致させ、要約だけで実変更を推測させない。

## 6. PR本文の推奨構成

```markdown
## 対応する指摘
- 元PRまたはIssueへのリンクと、指摘内容

## 変更箇所
- path/to/file — 見出しまたは関数名
- 変更理由

## 差分
```diff
- 修正前
+ 修正後
```

## 確認
- 実施した確認と結果
```

複数の独立した指摘がある場合は、指摘ごとに変更箇所と差分を分ける。

## 7. 確認と完了報告

変更の種類に応じた確認方法をIssueまたはPRに記録する。実施していない確認を実施済みとして記載しない。変更完了時の報告には次を含める。

- 作成・更新したIssue、マイルストーン、PR
- 変更したファイルと主な差分
- 実施した確認と結果
- 未解決の指摘や依存関係

PRを作った時点と、マージ・公開した時点を区別して伝える。
